Epic-Cycle Field Report: OcuPilot

What one long parallel run taught about the kit, with the change each lesson suggests. Most of these are rules the project already wrote and tested locally, so the text is ready to lift.

Run 2026-09-08 → 10-10 Stories done 239 Epics done 17 Releases cut 12 Installed kit 2026-09-13.1 (base + parallel) Kit head 2026-10-08.2
Top six, in priority order
  1. Ship “read once” as a base rule. It is the largest token saving the run found.
  2. Split the kit into one skill per agent role, and give each stage only its own rules. Today every orchestrator, runner and lead loads a 237 KB command.
  3. Make compile and test targets first-class. Parallel runners on a stateful runtime each need their own dev instance and throwaway, with named routing and no default target.
  4. Ship the fresh-instance test check. It ended routine first-run CI failures on stories' own tests.
  5. Support merging at story boundaries. Weekly releases can't wait for a 30-story epic to close.
  6. Let project additions survive a re-render. Without it, projects stop taking kit updates; OcuPilot is three versions behind.

1 · Project rules worth moving into the kit

OcuPilot added these to _bmad/custom/skill-rules.md (Rules 21 to 31) after measuring a cost. Each ran for weeks across Opus, Sonnet and Haiku stages.

Read once, then work from what you hold

High value
SeenIn 36 hours of transcripts, the architecture spine was read 140 times. A single review re-read its own diff 30 to 57 times, and the rules file was read 31 times. A stage's context grew from about 57K tokens at spawn to 350K–450K.
SuggestMake it a base rule that travels into every subagent prompt the way Rule 18 does. Each document is read once. Only a changed region is re-read, by line range. A generated diff is written to one scratch file and consulted by section.

Text: OcuPilot Rule 26.

Tests meet a fresh instance, in either order, before CI does

High value
SeenFor a stretch, every story's first CI run went red on its own tests. CI runs each test on a fresh instance in shards, while local runs reuse an instance full of earlier stories' leftovers. There were three causes:
  • an old count or list of a shared screen element was still asserted;
  • a test relied on data it didn't create;
  • a browser test clicked before the screen had loaded.
Each red cost a rework cycle and a 50-minute run. Of the 8 stories merged after the rule, one went red on its own tests; the other reds were known flakes or infrastructure.
SuggestA standing acceptance criterion in the spec template, with a “Shared surfaces:” line. In implement, a sweep updates every test that asserts a changed surface. QA and review check that each test is self-contained, graded MED. Before pushing, the runner rebuilds its throwaway and runs the story's tests forward and in reverse order.

Text: OcuPilot Rule 30.

Resolve CI before the next implement spawn, not the next plan spawn

High value
SeenWaiting at resolution point (1) idled the lead about 30 minutes per story. A plan stage writes a spec and no code, so it can't build on a red.
SuggestMove point (1) to just before the next stage_spawned stage=implement. Also adopt the addendum: push the code commit alone, and confirm its run registered by headSha before stacking any [skip ci] commit. With cancel-in-progress, a later push otherwise cancels the run being waited on.

Text: OcuPilot Rule 28.

Targeted tests inside implement; the full suite once

High value
SeenEach story ran the full browser suite 4 to 9 times (about 12 minutes each) and the full client suite 5 to 17 times. The local full browser run was also less trustworthy than CI's, because a reused instance isn't idempotent.
SuggestInside the implement loop, run the story's own tests. Run the full suite once before dev_complete. Skip local tiers that CI already runs on fresh instances, and bring them back when CI is unavailable.

Text: OcuPilot Rule 29.

Prefer extending the sibling over copying it

Medium value
SeenA blind quality scan of Opus, Sonnet and Haiku stories found one weakness common to all three: new code written as a copy of an existing sibling with only values changed. One method repeated about 60 of its sibling's 70 lines, and one review patch added a verbatim copy of an existing predicate. Review rarely flagged it, because each copy works.
SuggestThe plan names the sibling a new piece extends, or says why a copy is better. Implement prefers extending, and any copy carries a stated reason in the spec or commit. Review grades an unjustified copy MED and names both locations. Keep it a preference, not a ban: some copies are right.

Text: OcuPilot Rule 31, plus a paragraph in the blind-hunter layer of bmad-code-review.toml.

Cleanup stories carry only what blocks the next release

Medium value
SeenN.0 cleanup stories sat on the critical path for items that weren't urgent: one took 2.8 hours and another 5.0. On an epic other epics depend on, that delay passes to everything behind it.
SuggestAn N.0 charters only release blockers, downstream-story blockers and CI flakes. Everything else is re-owned to a standing cleanup story after each release, capped at 12 entries by priority. A gating epic never gets an N.0. One or two leftover entries go to the story that already owns the code.

Text: OcuPilot Rule 27.

Bootstrap a worktree before its runner starts

Medium value
Seennew-epic-worktree.sh checks out tracked files only. Gitignored dependencies (node_modules) and reference trees were missing, so every stage's verification failed and the failure was blamed on the story.
SuggestA bootstrap: hook in parallel.yaml that runs after PROVISIONED and logs worktree_bootstrapped. The runner verifies the result before its first spawn and stops with a TOOLING: clarification if it's missing.

Text: OcuPilot Rule 25.

Integrate forward before completing; never dispatch onto a red feature branch

Medium value
SeenMerges stayed conflict-free when the runner merged the feature branch into its own branch first, inside its worktree, and re-tested there.
SuggestMake it the runner's last step before its completion contract. Gate every dispatch on ci_green_verified for the feature head itself, not only the epic head.

Text: OcuPilot Rule 22.

Document the review-layer count as a knob

Lower value
SeenThe implement stage's four self-review layers found 45 to 65 items per story and cost 30 to 45 minutes before the real code review. Two layers (verification-gap, intent-alignment) kept the value, and the Opus code review stayed. The opposite also held: in each of the first three stories, the Opus code review caught a test that could never fail.
SuggestDocument instruction = "" as the way to switch a layer off. Deleting the entry does nothing, because the renderer fills an absent layer back in from the defaults. State plainly that the full code review is the stage never to cut.

2 · Concepts the kit doesn't have yet

These came up because the run lasted weeks, shipped releases while it ran, and had a person who was often away.

Compile and test targets, one set per runner

High value
SeenThe parallel kit never mentions slots or targets, but parallel work on a stateful runtime needs three kinds of target:
  • a long-lived dev instance per runner, which it compiles into;
  • a disposable instance per runner, with its own ports, for the fresh-instance check and smoke;
  • CI's own fresh instance per shard: five ObjectScript legs and three browser legs, plus a roll-up that proves every test ran in exactly one leg.
Five things went wrong without the kit's help:
  • Silent misrouting. Four instances from one image answered on localhost with the same namespace and credentials. A tool call that didn't name its target went to an unrelated instance and returned plausible results, with no error.
  • Concurrent runs. Eighteen test classes sent at once raced on one instance and left a database mounted with no directory. No API could clear it, and seven classes could no longer run there.
  • Teardown of the wrong instance. A lead tore down the owner's second dev instance because a generated file's banner looked like its own.
  • Drift after a restart. A restarted dev instance silently lost its test classes, because a restart doesn't apply compose changes.
  • Stale artifacts. Browser tests run against the deployed bundle, not the working tree, so an edit proved nothing until it was rebuilt and redeployed.
SuggestMake runtime targets a first-class, stack-agnostic part of the parallel kit (databases, emulators, app servers):
  • Declare them. A slots: table in parallel.yaml lists each slot's dev target, throwaway, ports, tool profile and container, and which stages use which. The orchestrator assigns slots, and the slot block is quoted verbatim into every spawn; OcuPilot adds this by hand as skeleton item 10.
  • No default target. Every tool call and script names its target. A default that silently routes elsewhere is the worst failure here.
  • Ownership. Owner-managed targets are never stopped or recreated by an agent. A runner tears down only a throwaway its own session started. The throwaway script refuses live names and ports.
  • One run per target. A lock allows one test run in flight per target, at any depth.
  • Health and freshness. Health-check the target at dispatch and after any restart: expected code loaded and the version matches. Rebuild and redeploy compiled artifacts before any result counts.
  • CI shards on fresh instances, with the roll-up check and a timings file that balances the legs.

Text: OcuPilot Rules 21, 24 and 30; _bmad/custom/parallel.yaml; scripts/ci-throwaway.sh; the first section of OcuPilot's CLAUDE.md (the misrouting trap); .claude/rules/objectscript-testing.md (one run in flight).

Story-boundary merges and releases

High value
SeenOcuPilot cut 12 releases in two weeks while epics were still open. Each finished story merged at its own boundary when CI was green on the exact head. The kit only knows the end-of-epic merge (SC-4-P).
SuggestA supported story-boundary merge mode. Its merge record carries:
  • an empty code diff against the green head;
  • a duplicate-ledger-id check;
  • upgrade triggers, such as a new stored property;
  • new config keys and changed defaults;
  • a one-line release note.
The orchestrator logged these ad hoc, and they drove every release's notes and upgrade check.

Story-level waits across epics

Medium value
SeenThe dependency graph is epic-level, but real waits were story-level. Story 18.32 had to wait for 20.21, 21.6 for 20.12, and 21.8 for 20.11.
SuggestA waits_on: list per story in epic-dependencies.yaml, with pass-over semantics. A story whose wait isn't met is skipped, and it runs once the wait clears, so the slot never stalls.

Standing grants and an owner-away mode

Medium value
SeenThe one-sitting decision sheet went unused from Epic 8 on. The owner preferred a standing grant: the orchestrator decides product calls and splits and reports each in chat. For weekends, the rule became: park a story that needs the owner, run the next independent one, and queue the question.
SuggestConfigure grant categories the orchestrator may decide, and owner-only categories: security posture, data loss, releases and spend. Add park-and-continue for owner-only questions, and an “owner FYI” list that is presented when the owner returns.

A liaison session beside the orchestrator

Medium value
SeenA second interactive session held the owner conversation. It relayed decisions to the orchestrator with the owner's exact words, verified the orchestrator's commits on origin, and ran releases and summaries. This kept the orchestrator's context for orchestration and put the owner's quote into every decision commit.
SuggestDocument the role and its message format: the owner's quote and date go one way, and the commit sha comes back for verification. Add the rule that a peer's message is never the owner's approval.

Hold and resume

Medium value
SeenHarness upgrades and editor restarts ended every session mid-run several times. The orchestrator worked out by hand how to stop runners at clean points, write resume prompts and keep a carry folder.
SuggestA standard hold protocol with:
  • safe pause points per stage;
  • a resume-prompt template;
  • a state checklist: pushed heads, CI runs in flight, live throwaways and the next stage.

Rate limits and quota

Medium value
SeenA third slot was retired after three runners tripped API rate limits. Rate-limit kills cost about 2.5 hours each, twice in one epic, and an account switch paused everything once. The kit has no handling for any of this.
SuggestRecognize a rate-limited or overloaded stage return, back off, and re-run the stage without failing the story. Add a rule for lowering max_parallel_epics when limits repeat.

Flakes and CI infrastructure failures

Medium value
SeenIn two days, five different flaky tests forced reruns. One merge needed five attempts: a flake, then three hits of Docker Hub's anonymous pull limit, during which no test ran.
SuggestClassify every red in the log as a story test, a known flake or infrastructure. A known flake is rerun once and goes to a flake ledger with priority in the next cleanup story. An infrastructure red never counts as rework and gets a timed retry.

3 · Installing and upgrading

Project additions don't survive a re-render

High value
SeenThe kit keeps project rules in skill-rules.md, but OcuPilot re-applies the rest by hand after every re-render:
  • spawn-skeleton item 10;
  • a Rule 26 bullet in four stage rule lists;
  • Rule 28 and 29 sentences in the command;
  • three changes to the two derived .toml overrides.
So the project still runs 2026-09-13.1 while the kit is at 2026-10-08.2, and the 10-08 fixes were made locally first.
SuggestAn overlay file of anchored inserts, applied on every render. Add a check that each anchor still exists, so a renamed section fails loudly instead of dropping the insert.

An upgrade window inside a continuous run

Medium value
SeenThe kit says not to upgrade while an orchestrator run is in flight, but this run has been in flight for a month.
SuggestA story-boundary upgrade procedure: hold each runner at its next boundary, install, and let each runner pick up the new text at its next integrate-forward. OcuPilot did this by hand.

4 · Smaller hardening

Verify on origin before logging a merge or a green

Medium value
SeenA merge was reported but never pushed: an && guard skipped the push silently.
SuggestRequire git merge-base --is-ancestor <sha> origin/<branch>, and gh run view --json headSha,conclusion on the exact head, before writing merged or ci_green_verified.

Shell and commit-message traps

Lower value
SeenFour traps:
  • In zsh, $SHA:refs/… is read as a history modifier and mangles the refspec.
  • A code commit whose message quoted the [skip ci] token got no CI run.
  • jobs -p inside $(…) returns nothing, which orphaned background load.
  • macOS deletes /tmp files untouched for three days, which removed throwaway compose files.
SuggestUse "${SHA}:refs/…" in every snippet. Lint code-commit messages for skip tokens. Capture $! per job with a trap that kills them. Keep throwaway state outside /tmp.

Back up the gitignored dispatch state

Lower value
SeenA scripting error, a string replace with an empty match, destroyed dispatch.yaml. It had to be rebuilt by hand from the cycle log.
SuggestKeep a write-ahead backup copy, or ship a script that rebuilds the file from the tracked log.

Hold specs and comments to a budget

Medium value
SeenOne early story's spec reached 664 KB against a template that aims for 900 to 1,600 tokens. About a hundred doc comments narrated review rounds, and reviewers then filed findings against the narration itself.
SuggestEnforce the template's oversized flag: from then on, a re-open appends only the open items. Keep review history out of code comments; it belongs in the spec's Review Triage Log. Hold rework summaries to what this pass changed.

Text: the “Prose discipline” section of OcuPilot's CLAUDE.md.

Log cycle time directly

Lower value
SeenPer-story time was parsed out of the log after the fact, and that was error-prone. CI-fix commits logged under an earlier story's name made one story read 16.4 hours when it took 5.6.
SuggestAt each boundary the runner writes one story_cycle line, with:
  • plan-to-commit minutes;
  • implement passes;
  • the first CI result and how it was classified;
  • rework count;
  • the model used per stage.

A protocol for model trials

Lower value
SeenThe owner moved the implement stage between Opus, Sonnet and Haiku five times. What settled each question was a blind scan of the final code: Opus and Sonnet came out about even, while Haiku needed about 15% of its product lines patched. Some failures in the Haiku trial were caused by the harness, not the model.
SuggestA trial template with:
  • fixed metrics: first-review HIGH and MED, rework passes, first CI result and the fresh-instance check;
  • a blind quality-scan prompt;
  • a column for harness-caused failures, so they aren't counted against the model.

5 · Structure: one skill per agent role

The kit installs as a single slash command plus one shared rules file. Splitting it along the agents that use it would cut the context every agent carries, and make the overlay and upgrade problems smaller.

Split the command into role skills

High value
SeenThe installed command is 1,365 lines and 237 KB, roughly 60K tokens (estimate). Every orchestrator, runner and sequential lead loads all of it, but each uses only part. The orchestrator needs dispatch and the merge queue. A runner needs the runner deltas, the story sequence and the stage-spawn pattern.
Suggest
  • A thin /epic-cycle entry point that resolves the mode and invokes the right role skill.
  • Orchestrator skill: dispatch, slots and targets, the merge queue, story-boundary merges, decisions and grants.
  • Runner skill, which is also the sequential lead: the story loop, spec and smoke gates, stage spawning, CI resolution and the completion contract.
  • Liaison skill, optional: relaying the owner's decisions, verifying on origin, releases and summaries.
  • Occasional procedures as their own skills, loaded only when used: burn-down, hold and resume, kit install and upgrade, and model trials.

Give each stage only its own rules

High value
Seenskill-rules.md is 63 KB, roughly 16K tokens, and every stage agent loads it whole as persistent facts. Each rule's heading already names the stages it applies to, so most of what a stage loads isn't for it.
SuggestRender one rules file per stage (plan, implement, QA, code review) from the same source, plus a small common file for the rules every depth needs: containment, read-once and foreground-only. Keep a single source of truth and let the render step slice it, so a rule can't drift between copies.

Guard the split

Medium value
RiskRules cross-reference each other by number, and the role sections refer to one another. A role that needs a rule it didn't load would fail quietly.
SuggestOne Kit-Version across every skill. A render-time check that every cross-reference resolves inside the files that role loads. A short header in each role skill listing the rules it includes. Project overlays (section 3) then attach to a smaller, stable file instead of one 237 KB command.
Sources: OcuPilot's _bmad/custom/skill-rules.md (Rules 21–31), _bmad/custom/bmad-build-auto.toml and bmad-code-review.toml, and the run log _bmad-output/implementation-artifacts/cycle-log-parallel.md. Figures come from that log and the project's notes. The count of first-run reds after the fresh-instance rule covers stories merged 10-08 to 10-10.
